# Dual AI Offer Agents — Muse Spark 1.3

## Trust boundary and customer journey

Shop → Bag → Check Prices → Final Offer → Accept or Keep Original → PayPal Sandbox. The saved 19-record Channel3 footwear catalog, 171 simulated size SKUs, cart fingerprint, original-price checkout, and PayPal server authorization are retained. The consumer does not select an internal pricing scenario.

On a footwear price check, the server validates product, size, SKU stock, quantity, currency and merchant prices before any model call. It uses saved Channel3 market snapshots; no new product discovery occurs. A bounded, server-generated JSON fact set (maximum six cart lines) goes to Agent A. Agent A advises on demand and margin. Agent B sees those facts and Agent A's structured advice and proposes one decision and integer-cent unit price per line plus a consolidated subtotal. The server rejects incomplete line sets, invalid totals, insufficient stock, stale market evidence, below-cost prices and merchant-policy violations. At most one sanitized revision request goes to Agent B. A failed model call or second invalid proposal yields no adjusted offer; independently authorized original-price checkout remains available.

The agents cannot save policies, inventory or payments. Their output is untrusted even when it conforms to the requested JSON schema. Acceptance and PayPal order preparation recompute the cart and AI policy from server records, and check session, offer status, expiration, SKU identity, evidence, and authorized totals. No live-money discount is allowed from variant-incomplete evidence: AI offers require explicit Sandbox demo assumptions.

## Agent instructions and model

The server uses the OpenAI-compatible JavaScript SDK pointed at Meta Model API (`https://api.meta.ai/v1`) and fixes the model to `muse-spark-1.3` in Standard mode. This spends Meta Model API credit, not OpenAI or Vercel AI Gateway credit. Meta documents [Responses API compatibility](https://dev.meta.ai/docs/protocols/responses) and [strict JSON Schema output](https://dev.meta.ai/docs/api-reference/responses/schemas). `agents/inventory-sales/SKILL.md` and `agents/market-offer/SKILL.md` are read from disk and supplied as instructions for their respective calls. Product descriptions, retailer prose, and URLs are not supplied as instructions or in the model fact set. Strict JSON schemas are requested and Zod independently validates returned data. No live Meta call or billable evaluation was made during this migration; a missing key or API failure safely falls back to the original price.

Agent A schema incident (2026-11-08, request `6w797-1794153540646-056354b7a6ac`): the response parsed as JSON, but Zod rejected its shape. The old log recorded no issue details, so the exact rejected field cannot be reconstructed. Static review confirmed the requested Agent A JSON Schema omitted Zod's string and array caps and nonnegative/safe-integer bounds; the requested schemas now derive from the Zod validators so they include those constraints without a second hand-maintained definition, and the instruction explicitly names every required field and enum boundary. New schema-failure logs include only an issue count, allowlisted field paths, allowlisted Zod issue codes, and safe expected type/enum categories (up to eight issues); they never include output values, raw issue messages, identifiers, or prompts. Low reasoning effort predates this incident, but the available log does not establish it as the cause. No repair call or automatic model retry was added; the original-price fallback remains in place. Because no live Meta request was made for this change, verify after deployment that the provider accepts the expanded strict schema and inspect only the safe diagnostic event if Agent A still fails.

## Merchant policy examples

- Overstock/no sales: product stock >50 and zero sales in 30 days. Merchant selects a 5% or 10% above-cost minimum with `AI_OVERSTOCK_MARKUP_BPS` (500 or 1000).
- Scarce/active: product stock <10 and sales on at least `AI_ACTIVE_SALES_DAYS` distinct days in 30 days. Floor is `max(cost, 85% of original retail)`.
- Normal: existing minimum-price and maximum-discount constraints apply, never below simulated acquisition cost.

The selected SKU must always have enough simulated stock. AI recommendations cannot change these conditions. The market's unknown shipping, fees and size equivalence remain explicitly unverified. A saved product-price reference can support only a clearly labeled Sandbox assumption, not an exact delivered-price match.

## Cost and latency controls

Muse Spark's internal reasoning counts toward the output-token cap and can add latency. Both advisory agents now request `reasoning.effort="low"`, which Meta documents for direct classification and formatting tasks; server-side policy checks remain authoritative. This is intended to reduce reasoning-token use and response time without increasing the 4,096-token cap or 20-second per-request wait. The 20 seconds limit how long the server waits for one Meta API response, not checkout or PayPal processing. See [Meta reasoning guidance](https://dev.meta.ai/docs/reasoning) and [Responses API parameters](https://dev.meta.ai/docs/protocols/responses).

Request-failure logs also include an allowlisted `errorType` and `nearDeadline` boolean. `nearDeadline=true` means the error occurred within one second of the configured 20-second wait limit; it is a clue, not proof that the SDK timed out. Error messages, stack traces, request bodies and credentials remain excluded.

One-item checks use at most two initial model calls (one per agent); only a rejected proposal permits one extra Agent B call. Up to six lines are batched in those same calls. Each model request uses a fixed 20-second timeout, zero automatic SDK retries, `store:false`, and a 4,096-output-token cap. Agent A insights are cached for five minutes on unchanged facts. Repeated identical session/cart checks reuse an offer for 60 seconds while still issued. Per-process concurrency is limited to two. Development has an in-memory daily call/spend guard; production uses the atomic `ai_offer_daily_budget` PostgreSQL table from migration `202610260001_ai_offer_budget.sql`. A production database failure denies model calls.

The application conservatively reserves $0.05 per model request and defaults to 40 calls and $1 estimated daily spend. The usage log contains model, input/output token counts, elapsed time and an **illustrative** estimate using Meta's published Standard-mode $1.25/M input and $4.25/M output token rates, [subject to change](https://dev.meta.ai/models/muse-spark). This estimate is not a billing guarantee. For a two-call check, the reserved application budget is $0.10; a single revision raises it to $0.15. Configure a project-level Meta budget and alerts separately—dashboard budgets may not be hard stops. Do not buy credits or enable auto-recharge for this demo.

## Internal diagnostics

The Meta API returned `status=incomplete` with `reason=max_output_tokens` and no text during the first live Agent A test at the previous 1,400-token cap. The cap is now 4,096 tokens per request; zero SDK retries and the existing daily request/spend reservation remain in place. Parsing-failure logs include safe input, output, and reasoning token counts when the provider supplies them, plus the configured output-token limit. These values help distinguish reasoning-token exhaustion from malformed final text without revealing model content. A higher cap may increase actual Meta charges; the application's fixed $0.05 reservation is an estimate, not a provider billing limit.

For a successful HTTP response that fails parsing, `ai_offer_model_failure.response` reports only safe metadata: response status, a whitelisted incomplete reason, whether text came from the SDK aggregate or a standard output message, text length, output item count, and content kinds. It never logs generated text or refusal text. Empty output, incomplete output, refusal, failed response, and non-JSON text have distinct categories. The parser accepts standard `output_text` message blocks if the SDK's aggregate text is empty; Zod and merchant policy still validate the result before any offer is authorized. Do not treat a response arriving from Meta as proof of a valid offer.

For model failures, `ai_offer_model_failure` records the agent, failing stage (`budget`, `instructions`, `request`, or `response_parse`), safe category (`budget_exhausted`, `concurrency_limited`, `budget_config_invalid`, `budget_backend_unavailable`, `budget_query_failed`, `instructions_missing`, `instructions_read_failed`, `timeout`, `connection`, `invalid_request`, `authentication`, `permission`, `rate_limit`, `provider_error`, `request_failed`, or `invalid_json`), elapsed milliseconds, an HTTP status if available, and a whitelisted network error code if present. Schema, line-set, subtotal, policy, and final authorization failures emit `ai_offer_validation_failure` with a fixed stage/category. Logs never include prompts, API keys, exception messages, provider response bodies, cart content, or sessions. One price check may make two model requests, plus at most one Agent B revision; the 20-second timeout applies to each request separately. A budget reservation is not proof of a completed billable Meta request.

The timeout is fixed at 20 seconds in code; an existing Vercel `AI_OFFER_TIMEOUT_MS` setting is ignored and can be removed after deployment.

The 19 footwear storefront prices equal the lowest eligible saved Channel3 observation for each product (positive USD, new, marked in stock, HTTPS merchant URL). Ties use merchant domain and URL for stable ordering. The saved merchant, URL, USD price, and retrieval timestamp are kept in `footwearSnapshots.priceReference`. NORTH/01 and all inventory, costs, sales, returns, and size availability are simulated; Channel3 supplies a historical product/price observation and is not the merchant. Saved observations do not establish current competitor stock, shipping, fees, or a delivered-price match.

Incident note (2026-11-08, request `6858v-1794145296425-17bc06ecaa6b`): the production Agent A request failed after 20,566 ms. The deployed log said `request_failed`, but OpenAI SDK v7.43.0's `APIConnectionTimeoutError` inherits `name: "Error"`, so the former name-based classifier could mislabel a timeout. The classifier now uses SDK class identity and logs only an allowlisted error type, category, HTTP status or network code, elapsed time, and deadline proximity. A near-deadline failure remains suggestive, not proof, of a timeout; confirm the precise cause from a post-fix classified event or provider-side request trace. There are no automatic model retries. The 4,096-token cap remains because a prior 1,400-token response was truncated; Agent A's single-line output is much smaller, but reasoning tokens also consume this cap. Low reasoning effort is under review in PR #21. No timeout increase is proposed without timing evidence, since a two-agent comparison can already take about 40 seconds before other checkout work. Original-price fallback and payment authorization remain independent of model availability.

When a footwear comparison falls back before calling the model, the server writes one `ai_offer_gate_disabled` warning to the Vercel Function logs. Its `checks` object contains only booleans (`agentEnabled`, `modelKeyConfigured`, `demoAssumptionsEnabled`, `paypalSandbox`); it never contains the key, environment-variable values, cart, or session. Filter logs for this event after a single Check Prices request to identify which prerequisite the deployed function actually sees. This event means no Meta API request was made. Remove the temporary gate warning after resolving the deployment configuration.

`/merchant/operations` shows simulated cost/stock/sales and the latest Agent A recommendation, Agent B proposal, policy outcome and final authorized unit. It requires Basic authentication (`merchant` as username, `MERCHANT_DEMO_ACCESS_TOKEN` as password, minimum 24 characters). The proxy returns 401 without credentials; the server layout independently withholds the data. The latest agent diagnostic is process-local and not a durable audit record. The public Merchant Demo and `/channel3-demo` routes remain available. Customer responses contain only safe explanations and a minimal offer ID/total/expiry, never acquisition costs, policies, prompts or model diagnostics.

## Automated validation

Mocked Agent A/B tests cover the three decisions, policy floors, invalid proposals, timeouts, rate limits, malformed output, conflicting advice, SKU substitution, multi-item totals, repeated checks, expiration, offer reuse, original-price isolation and payment amount integrity. Meta transport tests verify the endpoint, model, strict JSON format, and zero automatic retries without calling the API. PostgreSQL integration tests require `TEST_DATABASE_URL`. Live Meta Model API and PayPal Sandbox payments were not tested.

AI offer acceptance uses an exact four-field inventory-policy comparison (`version`, `overstockMarkupBps`, `activeSalesDays`, `maximumDiscountBps`) independent of JSON object key order. This is required because PostgreSQL JSONB reorders keys in the saved offer record. A real PostgreSQL integration test covers the comparison → JSONB reload → acceptance → checkout-preparation flow. Changed or missing fields still fail closed. The separate `merchant_pricing_policies` row is versioned, and `savePolicy()` intentionally keeps the existing row on a same-version conflict. This was not the cause of the JSONB acceptance error: acceptance first compared the offer's saved `policyConfig`, while the database policy ID and version matched. However, reusing a version with materially different policy-row content can leave that row stale; policy content changes need a deliberate version/migration plan. This fix neither overwrites the row nor changes its version semantics.

## Rollback and limitations

Set `AI_OFFER_AGENT_ENABLED=false` to stop model calls immediately; original-price checkout continues. Revert the PR to remove the UI and service path if needed; retain the budget table for audit or drop it separately after confirming no deployments use it. No Meta key was configured in the development environment, so live model behavior remains unverified. Channel3 snapshots are cached, variant-incomplete, and have unknown shipping/fees. Inventory, acquisition cost, sales, returns and NORTH/01 retail prices are simulated. Mocked tests do not prove live model quality or a real PayPal Sandbox payment.
