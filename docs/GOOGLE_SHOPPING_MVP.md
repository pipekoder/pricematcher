# Google Shopping observed-price MVP

This is a Sandbox-only AI offer flow. The 19 NORTH/01 product identities and storefront prices come from saved Channel3 observations; NORTH/01, SKU stock, costs, sales, and returns are simulated. Channel3 is not the seller. No Channel3 request is made by the footwear storefront or this Check Prices path.

When explicitly enabled, one click searches the first SKU in the cart using SerpApi `engine=google_shopping`, `gl=us`, `hl=en`, `no_cache=true`. The query uses trusted catalog brand/model/color and selected EU size. One provider request is issued, with no automatic retry; other cart lines may retain the original price. A new deliberate click starts a new search, while simultaneous requests for the same session/cart share an in-process pending comparison. Agent A merchant analysis and the bounded search run concurrently. The server filters identity and explicit size mismatches, out-of-stock listings, and non-new condition, then deduplicates, sorts by observed USD product price, and keeps the cheapest 20. Equal prices use a stable merchant/title/URL/ID tie-breaker. Unknown availability, preorder, and backorder remain eligible and retain their labels; stock status, variant confidence, and Sponsored status do not affect ranking. All 20 at most are passed to Agent B. A separate `engine=google_ads` call is not made or enabled. An inline result is labeled Sponsored only if an explicit Google `/aclk` tracking link is present; ordinary Shopping results are never inferred to be ads.

Supported fields from the [official SerpApi Shopping sample](https://serpapi.com/google-shopping-api) are `shopping_results`, `inline_shopping_results`, `title`, `source`, `price`, `extracted_price`, `product_id`, `product_link`, `link`, `tracking_link`, and `delivery`. SerpApi's [Ads API sample](https://serpapi.com/google-ads-api) documents separate sponsored shopping data, but no additional billable Ads request is in scope. Price is accepted only when a USD `$` formatted string matches `extracted_price` to the cent in the fixed US market; old/crossed-out and installment values are ignored. `product_link` can be a Google page, not a direct retailer checkout URL. Missing size, shipping, fees, stock, color, or merchant fields stay unknown. Google observations are advertised search-result prices, not independently checked live retailer prices or delivered totals.

The saved search batch is associated with the session and SKU in PostgreSQL, and a bounded normalized result snapshot is included in the AI offer record. Agent A sees simulated merchant facts; Agent B sees those facts, Agent A advice and Google observations, then suggests an integer-cent offer. The cheapest eligible observation is the default MATCH_LOWEST reference. Agent B may instead propose PARTIAL_MATCH or KEEP_ORIGINAL, but the server independently enforces the reference, SKU inventory, price floors, exact cart and session, policy version/content, totals, a five-minute Google evidence TTL, offer expiry and replay protection at acceptance and again before PayPal order preparation. A rejected or unavailable search/agent yields original-price checkout. No retailer scraping or second-stage stock/shipping verification occurs, so even an AI discount is labeled an unverified Sandbox merchant promotion, not a guaranteed like-for-like delivered-price match.

## Preview-only enablement checklist

1. Apply `202611080001_google_shopping_budget.sql` and all earlier migrations to an **isolated Preview PostgreSQL database**. Never point Preview to Production Supabase. `APP_ENV=production` and `PERSISTENCE_BACKEND=postgres` are required for paid-call budget enforcement across Vercel instances. Keep TLS verification enabled.
2. Configure server-only `SERPAPI_API_KEY` for an approved test SerpApi account, `GOOGLE_SHOPPING_MAX_SEARCHES_PER_DAY` (start at 1–3), and `GOOGLE_SHOPPING_REQUEST_TIMEOUT_MS` (1,000–20,000; default 10,000). Set `GOOGLE_SHOPPING_ENABLED=1` only for the isolated Preview after the database and budget are verified. No `NEXT_PUBLIC_` key is used.
3. Set independent Preview Meta credentials and budget, `AI_OFFER_AGENT_ENABLED=1`, `PRICEMATCHER_DEMO_ASSUMPTIONS=1`, `PAYPAL_ENVIRONMENT=SANDBOX`, and the existing secure session/database variables. Do not copy Production secrets. The Meta Agent A/B Schema PR #23 remains separately unmerged and must pass its controlled Preview compatibility check before reliance on live structured output.
4. Confirm one selected product/size sends exactly one SerpApi Shopping request, check `google_shopping_daily_budget`, `google_shopping_search_batches`, safe `google_shopping_search` log, Meta usage/failure logs, `agentMode`, and comparison UI. Do not infer AI success from HTTP 200. Without explicit approval, do not make live SerpApi or Meta requests or complete PayPal Sandbox payments.

The application budget reserves one count before each provider call and fails closed if the shared table is unavailable. A PostgreSQL advisory lock rejects another search for the same session/SKU within five seconds, across function instances. Search attempts, including failed requests, consume this conservative application allowance. SerpApi's [published pricing](https://serpapi.com/pricing) currently lists a 250-search/month free plan and a $25/month 1,000-search Starter plan; verify account-specific limits before enabling. A Google-backed check can consume one Agent A and one Agent B Meta request, with no Agent B revision; these remain subject to the separate existing Meta budget. Concurrent Agent A analysis may still consume a bounded Meta request if Google search fails. Worst-case request waits before database/UI overhead are roughly max(10 seconds Google, 20 seconds Agent A) plus 20 seconds Agent B, or 40 seconds. No live latency or SerpApi response compatibility is claimed from mocked tests.

## Manual Sandbox acceptance

- Use an isolated Preview and a test SKU. Compare once. Confirm the UI shows observed Shopping results, timestamp, Sponsored only when evidenced, unknown availability/shipping where absent, and distinct AI success/fallback status.
- Inspect one discounted offer's merchant policy and five-minute evidence expiry without exposing costs to shoppers. Change size, quantity, policy, or saved offer amount in isolated tests and confirm acceptance/preparation rejects it.
- Accept an authorized offer, then inspect the server-prepared PayPal Sandbox amount. Complete a payment only after separate explicit authorization; this PR does not do so. Check replay/idempotent capture and server-verified payment status using the existing PayPal QA procedure.
